## About me

I'm an independent developer who learns best by **building real things**.

What started with web development, UI experiments and smaller projects has gradually grown into work across desktop software, mobile clients, backend systems, developer tooling, security, CI/CD and systems written in Rust and C#.

I like projects where design and engineering meet.

Not just:

> *Does it work?*

but also:

> *Is the architecture understandable? Is the interface useful? Can the system be trusted? Can I still understand the decisions behind it six months from now?*

I'm still learning — and I want that to remain visible in my work.

The goal isn't to pretend I already know everything.

The goal is to keep turning curiosity into increasingly serious software.

## Why Nexus?

<sub>My main long-term project and the place where most of my ideas come together.</sub>

</div>

Nexus grew from a simple idea:

**I wanted software that helps me work without forcing every part of my workflow into a completely separate world.**

Planning, notes, tasks, files, coding and eventually intelligent assistance all feel connected to me.  
So I started experimenting with what a workspace could look like if those areas were designed as parts of the same system instead of unrelated tools.

That experiment became **Nexus**.

Today I treat Nexus less like a single app and more like an ecosystem in which I can explore:

- local-first software;
- desktop and mobile application design;
- shared runtime architecture;
- secure client/server boundaries;
- release and update infrastructure;
- developer tooling;
- product design;
- and eventually more capable planning and assistance systems.

### What Nexus means to me

Nexus is also where I deliberately push myself beyond what I already know.

Instead of staying inside one framework or one type of application, I use the ecosystem to learn how larger systems fit together:

```text
product idea
    ↓
user experience
    ↓
application architecture
    ↓
shared contracts
    ↓
security boundaries
    ↓
testing + CI
    ↓
release infrastructure
    ↓
real software
```

That process matters to me as much as the final application.

## Why Nexus Cerebri?

At some point, building interfaces for planning made me more interested in the **actual reasoning behind planning**.

A calendar can display events.

A task manager can store deadlines.

But deciding *when something should happen*, what information is trustworthy, which constraints are hard requirements and what an automated system should actually be allowed to change is a much deeper problem.

That became the starting point for **Nexus Cerebri**.

Cerebri lets me explore subjects that are very different from normal frontend development:

- temporal reasoning;
- deterministic planning;
- constraints and preferences;
- search spaces;
- typed evidence;
- authorization boundaries;
- explainability;
- and the relationship between deterministic systems and future learned components.

One principle behind the project is especially important to me:

> **An intelligent system should not gain authority simply because it produced a convincing answer.**

Planning, validation, authorization and execution should remain understandable and separable.

Cerebri is both a project and a way for me to learn those ideas properly.

## How I like to build

As my projects have grown, I've become more interested in the engineering around the code — not only the code itself.

<table>
<tr>
<td width="25%" align="center">

### 🔍 Explicit

Architecture and important boundaries should be understandable instead of hidden behind accidental behavior.

</td>
<td width="25%" align="center">

### 🧪 Verifiable

Important behavior should have tests, repeatable checks and evidence instead of relying only on confidence.

</td>
<td width="25%" align="center">

### 🔐 Defensive

Authentication, credentials, releases and execution authority deserve stronger boundaries than ordinary UI code.

</td>
<td width="25%" align="center">

### 📚 Documented

Important decisions should survive longer than the context in which they were originally made.

</td>
</tr>
</table>

### AI-assisted development

I use AI coding agents as part of my development workflow.

I see them as **engineering tools, not sources of authority**.

They can help with implementation, tests, documentation, analysis and repetitive work — but generated code still needs to fit the architecture and pass the same checks as everything else.

My goal is to get better at using agents for **bounded, reviewable work** while keeping important decisions, verification and release authority under deliberate human control.

## Where I want to go

<sub>This part is intentionally personal — and will probably change as I do.</sub>

</div>

I'm interested in becoming the kind of developer who can take an idea through the entire journey:

**concept → design → architecture → implementation → testing → security → distribution → real users**

I don't want to specialize only in making interfaces look good or only in making code technically complicated.

I want to understand how complete products are built.

### My current direction

- make Nexus increasingly coherent instead of simply larger;
- improve the quality of my architecture and technical decision-making;
- get deeper into Rust, systems programming and deterministic algorithms;
- understand security beyond surface-level best practices;
- build better development and release processes;
- become more deliberate about testing and review;
- learn how intelligent systems can assist people without hiding their reasoning or authority boundaries;
- keep shipping things instead of learning only through tutorials.
